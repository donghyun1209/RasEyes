# RasEyes — Development Roadmap (v2.2)

> **목표:** 폰 앱(iOS)에서 목적지를 음성/텍스트로 검색하면 Google Maps 경로를 받아, 턴바이턴 안내("오른쪽으로 가세요", "50m 직진")를 BLE로 Pi에 보내 기존 TTS로 읽어준다.
> **마감:** 2026-09-14 파리 개강 전 (출국일은 2.1과 동일하게 9/2로 가정 — 미확정, 부록 C)
> **문서 갱신:** 2026-08-19 (신설)
> **전제:** iOS 네이티브(Swift/SwiftUI) 확정. 모바일 개발 경험이 사실상 없고(Android/Java 경험만 있음, Flutter 등 미경험) 필요한 플랫폼도 iOS 하나뿐이라, 크로스플랫폼 프레임워크의 학습곡선을 얹기보다 단일 플랫폼 네이티브가 이 일정에서 더 안전하다고 판단(2026-08-19 논의).
> **관계:** `2.1_ROADMAP.md`을 대체하지 않는다. 2.1의 임박한 작업(8/20 체크포인트 — 둘러보기 모드 실기 검증)이 우선이고, 이 로드맵의 Phase 1은 Pi가 필요 없어 병행 가능하다.

## 0. 왜 v2.2인가

- **버튼 재할당은 하지 않는다.** 물리 조작 수단(전원 버튼 1개 → 둘러보기 모드 토글)은 그대로 유지한다. 길안내는 폰이 GPS 경로 진행에 따라 능동적으로 Pi에 지시를 보내는 구조라, 애초에 버튼이 관여할 지점이 없다.
- **둘러보기 모드를 없애지 않는다.** 둘러보기 모드(실내·정지·즉석 공간 인지, "여기 벽 있어?")와 이 기능(실외·이동 중·목적지까지 경로 안내)은 서로 다른 문제를 푼다. 겹치는 영역이 없다.
- **"100% on-device, 외부 API/Cloud 금지"(CLAUDE.md §1)에 대한 명시적 예외.** 이 원칙은 착용 기기(Pi)의 인지 파이프라인(비전·ToF 추론)에 적용되는 것으로 좁혀 해석한다. GPS·지도·경로 계산은 폰에서 이뤄지고 애초에 클라우드 없이는 성립하지 않는 영역이다(오프라인 지도는 스코프 밖, 부록 D). Pi 쪽은 여전히 100% on-device를 유지한다 — Pi는 짧은 방향 문자열만 받아 발화할 뿐, GPS·지도 원본 데이터는 Pi에 들어오지 않는다.

**0-3 — Google 로그인 재검토 제안.** Google Maps/Directions API는 개발자가 발급한 API 키로 인증하는 구조라, **최종 사용자(본인)가 앱에서 Google 계정으로 로그인하는 것과는 별개다.** 카카오/네이버 대신 구글을 쓰기로 한 이유(해외에서도 동작)는 API 키 선택만으로 이미 충족된다. 1인 개인용 앱에서 로그인 화면은 OAuth 동의 화면·토큰 갱신·Google Cloud Console 클라이언트 등록까지 딸려오는 별도 작업이라 **뺄 것을 제안한다** — 즐겨찾기 목적지를 여러 기기에서 동기화하는 등 구체적으로 필요한 이유가 있으면 유지. 최종 결정은 사용자 몫.

**0-4 — Apple Developer Program($99/년) 가입 여부.** 가입 안 하면 실기기 설치용 무료 서명(Free Provisioning)은 **7일마다 Xcode로 재서명**해야 한다 — 파리에서 노트북 없이 한 주 이상 지나면 앱이 멈춘다. 학기 내내 쓸 생각이면 가입을, 개강 전 완성 자체가 목표면 일단 무료로 시작하고 나중에 결정해도 된다.

## Phase 2 · BLE 통신 계층 (Pi 하드웨어 필요 — 최고 리스크 구간)

⚠️ **가장 먼저 스파이크로 검증한다.** Pi(Linux/BlueZ)가 BLE **주변장치(Peripheral)** 역할로 GATT 서버를 여는 것과, 폰이 **중심장치(Central)**로 스캔·연결·특성 write 하는 것 — 이 최소 왕복 하나만 먼저 되는지 확인한다. VLM 실험 때(2.1 §2-D) "PC에서 품질부터, 이식은 나중"으로 순서를 갈라 몇 주를 아낀 것과 같은 이유다 — 여기서 막히면 이후 단계가 전부 무의미하다.

| # | 작업 | 파일(제안) |
|---|---|---|
| 2-1 | (0-2 확인 후) Pi BLE peripheral 스파이크 — 고정 문자열 하나 advertise → 폰이 연결해서 읽기 성공 여부만 확인 | `scripts/ble_peripheral_spike.py` |
| 2-2 | 프로토콜 설계 — 짧은 구분자 문자열 권장(예: `RIGHT|50`). BLE 기본 MTU가 작아(~20바이트) JSON 같은 장황한 포맷은 단편화 리스크 | |
| 2-3 | Pi 쪽 HAL — 기존 HAL 패턴대로 Mock/HW 분리 | `comm/ble_nav_hal.py`(제안) |
| 2-4 | 폰 쪽 `CBCentralManager` 스캔·연결·자동 재연결 | |
| 2-5 | 연결 끊김은 예외 없이 조용히 무음 처리 — 메인 루프·비전·경보 파이프라인에 영향 0 (ToF I2C 실패와 같은 fail-soft 원칙, CLAUDE.md §3) | |
| 2-6 | iOS 백그라운드 동작 — "Uses Bluetooth LE accessories" 백그라운드 모드 + 위치 "항상 허용" 권한. 화면 꺼진 채 걷는 걸 감안하면 필수 | Info.plist |

**완료 기준:** 폰 화면을 끄고 주머니에 넣은 채로 Pi가 방향 문자열을 계속 수신한다.

## Phase 3 · 안내 발화 통합

| # | 작업 | 비고 |
|---|---|---|
| 3-1 | Pi가 받은 방향 문자열을 문장으로 조립(`"Turn right in 50 meters"`) 후 기존 TTS(`ResidentAudioStream`)로 큐잉 | `main.py` |
| 3-2 | **우선순위 — 장애물 경보가 항상 이긴다.** 네비 안내는 `interrupt=True`를 쓰지 않는다(그건 HIGH 장애물 경보 전용, CLAUDE.md §7) — 네비 중에 HIGH가 뜨면 경보가 밀고 들어가고, 네비는 뒤에 이어서 나온다 | |
| 3-3 | **네비 안내도 밀릴 수 있다 — 둘러보기 모드가 이미 겪은 문제(2.1 §2-E ①)와 같은 종류.** GPS 갱신이 빠른데 발화가 못 따라가면 오래된 지시가 늦게 나와 엉뚱한 시점에 방향을 말한다. 새 지시가 도착했는데 이전 네비 지시가 아직 재생 전이면(`clear()`로 비우고) 최신 것만 말하는 식으로 설계 — 단 장애물 경보가 재생 중일 때는 절대 같이 지우면 안 됨(3-2와 충돌) | |
| 3-4 | 둘러보기 모드 중에는 네비 발화를 보류 — 둘러보기는 사용자가 능동적으로 요청한 상태라 우선순위가 더 높다 | |
| 3-5 | 회귀 테스트 — 네비 발화가 장애물 경보를 절대 선점하지 않는지, 오래된 네비 지시가 경보를 지우지 않는지 | `tests/test_ble_nav.py`(가칭) |
