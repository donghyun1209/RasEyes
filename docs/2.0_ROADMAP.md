## 확정된 원인

**① 카메라 노출·AWB가 실질적으로 미제어 — 최상위 원인**

클립 프레임 육안 확인 결과 완전 화이트아웃 / 거의 암흑 / 전면 녹색 캐스팅 / 모션 블러가 혼재. 코드에서 원인 확인:

```
vision/csi_camera_hal.py:87-90 — 해상도·FPS·버퍼만 설정. AE/AWB 제어 없음.
```

프레임당 탐지 밀도가 **0.64건(07-28) → 0.05건(07-29)** 으로 13배 악화. 모델 문제가 아니다 — 정상 노출 프레임에서는 여전히 person을 conf 0.79로 탐지한다.

**② `탐지 0개`가 `저조도`로 오분류됨 — 신규 발견**

```python
# fusion/engine.py:83
max_conf = max((d.confidence for d in detections), default=0.0)
tof_only = max_conf < effective_min_conf   # 탐지 0개 → 0.0 < 0.4 → 무조건 True
```

빈 장면(장애물 없음)과 저조도(카메라 실명)가 구분되지 않는다. 그 결과 객체 확인 게이트가 우회되고 ToF 숫자만으로 경보가 나간다. `tof_only_ratio` 1.00의 직접 원인.

**③ ToF 값이 경보로 승격되는 구조**

거리 중앙 156cm / p25 120cm / p75 193cm — MID 임계(150cm)와 해제선(180cm) 사이에 정확히 걸쳐 밴드를 **분당 10.1회** 왕복. 매 교차가 정당한 "신규 진입"으로 판정된다. 발화 간격 중앙 **1.2초**(55%가 2초 이내)로, 리마인더(5초)가 아니라 재-에스컬레이션이 대부분임을 확인.

**④ 세션 간 비교가 교란됨**

세션1(분당 29.4회)과 세션2(분당 11.0회)의 차이는 정책 효과가 아니라 **거리 분포 차이**(중앙 156cm vs 201cm)다. 상위 원인이 살아 있는 한 어떤 파라미터를 고쳐도 효과 측정이 불가능하다 — **이것이 Phase 5의 작업 순서를 강제한다.**

## 부수 관측

- **마운트 각도 의심** — 클립에서 지면·보도블록이 프레임의 절반 이상. 상단 사각지대(가슴~머리) 제품인데 하향 정렬일 가능성. ToF도 동축이라 지면 반사가 밴드 왕복의 원인일 수 있음. **착용 상태 물리 확인 필요.**
- **CSV 말미 잘림** — 세션2 마지막 행이 쓰다 만 상태(`202`)로 종료. 프로세스 비정상 종료 흔적.
- 저전력 모드 진입이 잦음(세션2 fallback 69.6%). 4-e로 ToF 단독 전환 연쇄는 끊겼으나 저전력 자체는 빈발.

### 5-1-1. V4L2 컨트롤 조사 결과 (2026-07-29, Pi 실측)

**결론: 자동 노출(AE)·자동 화이트밸런스(AWB)를 켜는 스위치는 존재하지 않는다. 직접 구현해야 한다.**

**① 캡처 장치 `/dev/video11` (rkisp mainpath — `CSI_DEVICE_PATH`, 코드가 여는 장치)**

```
pixel_rate  (int64)  read-only, volatile
```

제어 가능한 항목이 **하나도 없다.** ISP 단에서 노출·WB를 건드릴 수 없다.

**② 센서 subdev `/dev/v4l-subdev2` (OV13855 — `CSI_SENSOR_SUBDEV`)**

| 컨트롤 | 범위 | 현재값 |
|---|---|---|
| `exposure` | 4 ~ 3210 | **3000** (상한의 93%) |
| `analogue_gain` | 128 ~ 1984 | **1984 (최대치)** |
| `vertical_blanking` | 78 ~ 29631 | 78 |
| `link_frequency` / `pixel_rate` | — | read-only |
| `test_pattern` | 0~4 | Disabled |

**있어야 하는데 없는 것:** `auto_exposure`(`exposure_auto`), `white_balance_auto`, `red_balance`/`blue_balance`, `brightness`, `contrast`, 디지털 `gain`. 즉 **수동 노출·게인만 노출되어 있고 자동화 계층이 통째로 없다.**

**③ Rockchip 3A 데몬 (rkaiq) — 미설치**

| 항목 | 상태 |
|---|---|
| `rkisp_3A_server` / `librkaiq` | ❌ 없음 |
| 관련 systemd 유닛 | ❌ 없음 |
| `/etc/iqfiles/` 튜닝 파일 | ⚠️ 3개 존재하나 **OV13855용 없음** (`imx219` / `ov13850` / `ov5647`만) |

RK3588은 AE/AWB를 커널이 아니라 유저스페이스 3A 데몬이 담당하는 구조인데, 그 데몬이 설치돼 있지 않고 우리 센서(OV13855)용 IQ 튜닝 파일도 없다. `ov13850`은 이름만 비슷한 **다른 센서**라 그대로 쓸 수 없다.

**→ 선택지 2개 (다음 작업 시 결정)**

| 안 | 내용 | 비고 |
|---|---|---|
| **A. 직접 AE/AWB 루프** | 이미 받고 있는 프레임의 밝기·채널 평균을 재서 `exposure`/`analogue_gain`을 v4l2 subdev로 되먹임. 녹색 캐스트는 소프트웨어 WB 게인으로 보정 | 의존성 없음, 우리가 전 구간을 통제. 수렴 속도·헌팅(진동) 튜닝 필요. **1순위 후보** |
| **B. rkaiq 도입** | 3A 데몬 설치 + OV13855 IQ 파일 확보/작성 | Rockchip 정식 경로지만 IQ 파일이 없어 사실상 새로 튜닝해야 함. 부담 큼 |

**추가 발견 — 현재 설정이 야외 최악 조건이다.** `analogue_gain`이 **최대치(1984)**, `exposure`도 상한의 93%로 박혀 있다. 실내에서 최대한 밝게 맞춰놓은 값이라 직사광에서 화이트아웃이 나는 것은 필연이다. AE 루프를 만들기 전이라도 **게인·노출 상수를 낮추면 야외는 즉시 개선**되지만 그만큼 실내가 어두워진다 — 고정값으로는 양쪽을 만족시킬 수 없다는 것이 AE가 필요한 이유 그 자체다.

### 5-3 세부 — 이동평균 필터 호출 주기 버그 (07-28 발견, 미해결)

`FusionEngine._filter.update()`가 메인 루프 주기(66ms)로 호출되는데 ToF 폴링은 200ms다. **같은 값이 3번씩 버퍼에 들어가 window=3이 담는 실제 센서 샘플은 1~2개뿐**이다. `CLAUDE.md` §3이 규정한 "3샘플 이동평균"이 사실상 동작하지 않는다. 07-28에는 정책 효과와 뒤섞이지 않도록 의도적으로 손대지 않았고, 5-3에서 처리한다.

야외에서 비전은 사실상 실명(`tof_only` 96%)이고 ToF 점프율은 오히려 악화됐다. **AlertPolicy는 경보 횟수를 줄인 것이지 탐지를 정확하게 만든 것이 아니다.** 지금의 정적은 "정상 동작"과 구별되지 않는다.
