## 0. 방향 전환 요약 (2026-08-06)

### 바뀐 것

| | 이전 | 지금 |
|---|---|---|
| 보는 곳 | 머리 높이 **상단만** | 지면 + 정면 + 머리 높이 |
| 지면 측정 | **오염원** (억제 대상) | **신호** (측정 대상) |
| 사용 방식 | 걷는 중 수동 경보만 | 걷는 중 선행 감지 + 멈춰서 360° 스캔 |

### 목표 문장

> **지팡이가 닿는 곳을 2~3m 먼저 보고, 지팡이가 못 닿는 머리 높이까지 본다.**

**"지팡이 대체"는 목표로 잡지 않는다.** 기술이 안 돼서가 아니라 실패 허용도 때문이다.
8/6 로그에서 비전 실명 7.2%, FPS fallback 3.9%였다. 보조 기기면 괜찮은 숫자지만,
대체품이면 받쳐줄 게 없어서 안전 문제가 된다. 부팅 시간·배터리·발열 스로틀도 마찬가지다.
**도달 불가능한 기준을 잡으면 또 "안 됐다"로 끝난다.**

### 이 전환으로 없어지는 일

- ❌ ToF ROI 상반부 자르기 (`TOF_ROI_ENABLED`) — 지면을 잘라내는 작업이라 새 방향과 정반대
- ❌ MID 억제 로직 튜닝 — 지면이 신호가 되면 억제할 이유가 없다
- ❌ "벽인가 장애물인가" 추론으로 구분하기 — 센서가 직접 알려주게 만든다 (귀국 후 STEP 3에서, §6 참고)

**할 일이 늘어난 게 아니라 줄었다.**

## 1. 8/6에 알아낸 것 (읽고 넘어가기)

### 1-1. 경보의 67%는 비전 근거가 없었다

클립 30개 중 **20개가 저장 프레임에 탐지 0개**. ToF가 100cm 이내를 읽었고 YOLO는
벽·지면을 클래스로 갖고 있지 않으니, "비전 정상 + 탐지 0개 → HIGH" 규칙에 걸려 발화했다.

> **새 전제에서는 이게 문제가 아니다.** `145014`(골목 벽 68cm)는 지팡이라면 짚었을 벽이다.
> 이전에는 오탐이었지만 지금은 유효한 감지다. **다만 말하는 방식은 바뀌어야 한다** (→ STEP 4).

### 1-2. 말하는 물체 이름이 화면에 없다 (80%) — 이건 여전히 버그

경보 라벨과 그 프레임의 실제 탐지가 **30개 중 24개(80%) 불일치**.

| 시각 | 발화한 라벨 | 그 프레임의 실제 탐지 |
|---|---|---|
| 143922 | person | 없음 |
| 144023 | bus | refrigerator, apple |
| 144358 | **obstacle** | **bus:0.59** ← 반대로 틀림 |
| 144741 | vase | vase:0.85 ✅ (제대로 맞은 케이스) |

**원인:** `main.py:653`

```python
vision_ts, last_frame, last_detections = self._vision_q.get(timeout=_vision_wait)
```

큐가 비면 timeout이 나고 `last_detections`는 **이전 루프 값을 그대로 유지**한다.
메인 루프 15Hz를 비전 워커가 못 따라가면 낡은 결과로 계속 말한다.

> **스캔 모드에서는 이 문제가 구조적으로 사라진다** — 버튼을 누른 시점에 새로 동기 캡처하면 되기 때문.
> 그래서 별도로 고치지 않고 STEP 4에서 함께 해결한다.

### 1-3. 마젠타 캐스팅 — 진짜 버그지만 오탐 원인은 아니다

햇빛/조명 부분이 핑크색 (화면의 5~19%). 원인은 AWB가 이미 포화된 흰색(255,255,255)에도
G 게인(≈0.74)을 곱해서 → (255, 189, 255) = 마젠타.

**마젠타를 지우고 YOLO를 다시 돌려봤더니 탐지가 거의 안 바뀌었다.** 성능 영향 없음. (→ STEP 6 전 8-1에서 수정)

한편 AWB 본체는 **성공했다**: 비포화 영역 R/G=0.98~1.03. 8/4의 0.56에서 제대로 잡혔다.

### 1-4. ⚠ 확인이 필요한 이상한 숫자

8/4 로그에서 "유효 측정의 92%가 100~124cm에 몰렸다"를 **지면 반사로 해석**했는데,
기하학적으로 앞뒤가 안 맞는다.

가슴 높이 130cm에서 지면까지의 **직선 거리는 최소 130cm**다 (바로 발밑을 봐도).
그런데 측정값은 100~124cm였다. **지면이라면 나올 수 없는 값이다.**

가능성:
1. 실제 장착 높이가 생각보다 낮다 (허리 근처?)
2. 이미 상당히 아래로 기울어 있다
3. **옷·가방끈·팔 같은 자기 몸을 재고 있다** ← 이 경우 각도 조정으로 안 고쳐진다

**STEP 1에서 장착 높이와 각도를 실측해서 먼저 가려야 한다.** 여기가 틀리면 그 위의 계획이 다 흔들린다.

## 2. STEP 1 — 장착 높이·각도 재고, 사거리 재기 (1시간) ⭐ 여기서 시작

부품 살 필요 없이 **지금 하드웨어로 하는 검증**이다. 돈 쓰기 전에 전제를 확인한다.

### 1) 줄자로 두 개만 잰다

```
h = 센서 장착 높이 (바닥 → 센서)          128 cm
θ = 현재 아래로 기울어진 각도 (수평이 0°)  약간 아랫쪽(잘 모르겠음. 약간은 배제해야할듯)
```

각도는 스마트폰 수평계 앱을 센서 면에 대면 된다.

**이걸로 1-4의 이상한 숫자가 풀린다.** 만약 h=130cm인데 측정이 110cm로 나온다면
지면이 아니라 **자기 몸을 재고 있는 것**이고, 그럼 장착 위치부터 바꿔야 한다.

### 2) 실외 사거리를 잰다

**야외에 와이파이가 없어도 된다.** 스크립트는 I2C로 센서와 통신하지 SSH가 필요한 게 아니라서,
집 와이파이에서 시작만 해두고 끊어도 계속 돈다.

```bash
ssh raseyes
sudo systemctl stop raseyes.service        # ※ sudo라 직접 실행
nohup bash -c "sleep 120 && python3 scripts/tof_range_bench.py --mode long --seconds 120" > ~/tof_outdoor.log 2>&1 &
disown
exit
```

`sleep 60`은 명령 치고 밖으로 나갈 시간을 버는 것(필요하면 조정). 나가서 센서를 밖으로 향해 들고 있다가,
측정 끝날 때쯤(총 120초 후) 다시 들어와 확인한다:

```bash
ssh raseyes
cat ~/tof_outdoor.log
```

**밖에서, 햇빛 아래에서** 재야 한다. VL53L1X는 실내에서 4m를 봐도 직사광에서는
절반 이하로 떨어진다. 이 숫자가 다음 표에서 각도를 정한다.

```
실외 유효 최대 거리 R =  cm
```

### 2-1) LONG이 불안정하면 SHORT도 재본다

**2026-08-07 실측: LONG 모드는 직사광에서 "R 이내 안정 / R 초과 OoR" 경계 없이 전 구간이
불안정했다.** 서비스 충돌(`raseyes.service` 미종료로 같은 I2C 센서를 동시에 잡음)과 배선
접촉 불량(I2C `OSError: [Errno 6] No such device or address`)을 차례로 배제했는데도
73~502cm 전체에서 연속 샘플의 70%+ 가 50cm 넘게 튀었다. 이러면 R을 정할 수가 없어서
3)의 표를 못 쓴다. SHORT은 주변광 내성이 낫다고 알려져 있으니 같은 조건으로 재본다.

**측정 전 체크리스트 (LONG 재면서 겪은 실수들):**
- [ ] `raseyes.service`가 확실히 `inactive`인가 (`systemctl is-active raseyes.service`) —
      켜진 채로 재면 서비스가 같은 센서를 동시에 잡아 값이 튄다. **재부팅하면 자동으로
      다시 켜지므로** 재부팅 후엔 반드시 재확인.
- [ ] 센서 **몸체와 배선(커넥터)을 둘 다** 고정했는가 — 손으로 들면 배선이 흔들려
      I2C 통신이 끊기고, 값도 튄다.
- [ ] 측정 120초 동안 시야에 사람·차 등 **움직이는 게 하나도 안 지나가는** 방향인가.

```bash
ssh raseyes
cd ~/RasEyes
nohup bash -c "sleep 120 && python3 scripts/tof_range_bench.py --mode short --seconds 120" > ~/tof_outdoor.log 2>&1 &
disown
exit
```

`sleep 120`은 밖으로 나가 자리 잡을 시간. 끝나면:

```bash
ssh raseyes "cat ~/tof_outdoor.log"
```

**판단:** SHORT도 LONG처럼 전 구간에서 튀면 각도 문제가 아니라 센서의 야외 한계이므로
STEP 1을 더 진행하기 전에 재검토가 필요하다. SHORT이 안정적이면 그 유효 최대 거리를
`R`로 놓고 3)의 표로 넘어간다.

### 3) 표에서 각도를 고른다

지면을 `d`미터 앞에서 보려면 필요한 각도와 빔 거리다 (h=130cm 기준):

| 지면을 볼 거리 `d` | 아래로 기울일 각도 θ | 빔이 실제로 재는 거리 |
|---|---|---|
| 1.5 m | **41°** | 199 cm |
| 2.0 m | **33°** | 239 cm |
| 2.5 m | **27°** | 281 cm |
| 3.0 m | **23°** | 327 cm |

**"빔이 실제로 재는 거리"가 위에서 잰 `R`보다 작아야 한다.** 크면 OoR만 나온다.

> 예) R = 240cm로 나왔다면 → **d=2.0m, θ=33°** 를 고른다.
> 지팡이 도달 거리가 1.2m 정도니 2.0m면 **0.8m 먼저 아는 것**이다. 의미 있다.

계산식 (h가 130이 아니면):
```
θ = atan(h / d)          빔 거리 = √(h² + d²)
```

> **참고:** FoV가 27°라 빔은 점이 아니라 원뿔이다. 2m 지점에서 지름 약 1m를 평균한다.
> 지면 감지에는 오히려 유리하다 (작은 돌멩이에 반응 안 함).

### 4) 그 각도로 고정하고 30분 걷는다

**확인할 것은 하나다 — 계단·연석에서 거리가 튀는가.**

```
평지     : 지면까지 일정 (선택한 빔 거리 근처에서 안정)
내리막/계단: 반사면이 멀어짐 → 거리 급증 또는 OoR
턱/장애물 : 반사면이 가까워짐 → 거리 급감
```

**일부러 계단·연석·경사로를 지나가고, 지나간 시각을 메모해둔다.**

```bash
bash scripts/pull_logs.sh
python scripts/analyze_logs.py logs_archive/<새_파일>.csv
```

메모한 시각의 `tof_raw_cm`을 CSV에서 직접 찾아본다.

## 3. STEP 4 — 360° 스캔 모드 (이번 사이클 핵심)

### 아이디어

> 버튼을 누르고 **가만히 서서 한 바퀴 돈다.** 기기가 주변에 뭐가 있는지 하나씩 말해준다.

### 왜 좋은 아이디어인가

**오늘 실패한 거의 모든 항목이 스캔 모드에서는 사라진다.**

| 오늘의 문제 | 스캔 모드에서 |
|---|---|
| 경보 분당 10회 (KPI 1회) | 사용자가 요청했을 때만 → **"오탐" 개념 자체가 약해짐** |
| 라벨 80% 불일치 | 버튼 누른 시점에 **새로 동기 캡처** → 낡을 일이 없음 |
| 노출 상한 89.7% (모션블러) | **서 있으니 블러 없음.** 여러 장 찍어 제일 선명한 걸 고를 수도 있음 |
| 레이턴시 500ms 제약 | 사용자가 기다리는 중 → **1초 써도 됨** |

그리고 이건 **"굳이 쓸까"에 대한 답이 되는 기능**이다. 걷는 중 경보는 지팡이와 겹치지만,
"여기가 어디고 주변에 뭐가 있나"는 지팡이가 못 하는 일이다.
낯선 공간에서 방향 잡기는 실제로 큰 어려움이다.

### 이미 있는 것

`sensor/button_handler.py`가 **이미 구현돼 있다.** gpiod 2.x, 커널 디바운스, edge 이벤트
블로킹 대기까지 제대로 돼 있고 지금은 `_toggle_mute`에 물려 있다 (GPIO 26, `/dev/gpiochip1`).

**⚠ 확인 결과 실제 버튼은 안 달려 있었고(코드만 있고 미배선), Britz 스피커 버튼은 납땜이라 추출 불가.**
결국 저렴한 택트 스위치를 하나 주문하기로 함 — 개당 수백~수천원, 로켓배송 등으로 1~2일이면 온다.
**STEP 2(센서)와는 리스크 급이 다르다 — 이건 크리티컬 패스에 안 걸린다:**

- 스위치가 오기 전까지: 아래 "구현 순서" 2~5번(상태 머신·동기 캡처·중복 제거·발화)을
  **소프트웨어 트리거**(예: SSH로 `kill -USR1 <pid>` 신호를 보내 스캔 콜백을 직접 호출)로 먼저 만들고 검증한다
- 스위치 도착 후: 1번(배선)만 마지막에 붙인다 — 15분짜리 작업

즉 주문 여부가 일정에 영향을 주지 않는다. 지금 할 일은 (1) 스위치 주문, (2) STEP1이 아직이면 STEP1,
(3) 끝났으면 소프트웨어 트리거로 STEP4 로직 개발 시작 — 셋을 병행한다.

지금 핸들러는 FALLING edge만 본다. `Edge.BOTH`로 바꾸고 눌린 시간을 재면 짧게/길게가
갈린다 — 10줄쯤이다.

- **짧게 = 스캔** (자주 쓰는 기능)
- **길게 = 음소거** (드물게 쓰는 기능)

롱프레스는 진입할 때 짧은 비프로 피드백을 준다 (`audio/prerendered_tts.py`에 사전 렌더링 구조가 이미 있다).

### 진짜 어려운 부분 — 중복 제거

한 바퀴 돌면 **같은 의자가 수십 프레임에 나온다.** 그대로 읽으면
"의자, 의자, 의자, 의자..." 가 된다. **이게 이 기능의 핵심 난이도다.**

해결하려면 **각 탐지가 어느 방향에서 나왔는지**를 알아야 한다. 두 가지 방법:

**방법 A — IMU 추가**

자이로/가속도 센서(MPU6050 등, I2C, 저렴)로 **회전 각도(yaw)** 를 추적한다.

```
탐지를 (라벨, 방위각)으로 기록
    → 같은 라벨이 ±15° 안에 모이면 같은 물체로 묶음
    → "오른쪽 45도에 의자" 처럼 방향까지 말할 수 있음
```

**중복 제거와 방향 안내가 같은 데이터로 동시에 해결된다.** 다만 이것도 부품 구매라 이번 사이클엔 보류.

**방법 B — IMU 없이 (시간 기반) ← 이번엔 이걸로**

"천천히 한 바퀴 도세요" 안내 후 정해진 시간(예: 8초) 동안 수집하고,
경과 시간을 방위각으로 근사한다. 회전 속도가 일정해야 해서 부정확하다.

> 추가 부품(IMU) 없이 오늘 시작할 수 있다. 정확도가 아쉬우면 방향 없이 목록만 말해도 된다 —
> IMU 업그레이드는 귀국 후.

### 그 외 설계 결정

**말하는 개수를 제한한다.** 복잡한 공간이면 20개가 나온다. 다 읽으면 1분이 걸린다.
- 가까운 것부터 **최대 5개**
- 같은 라벨이 여럿이면 묶어서 ("정면에 의자 셋")

**거리는 ToF 원뿔에 들어온 것만 안다.** 회전 중 ToF는 정면 한 점만 잰다.
그 밖의 물체는 거리 없이 방향만 말하거나, bbox 크기로 대충 추정한다.
- "정면 2미터에 의자" (ToF가 잡음)
- "오른쪽에 자동차" (거리 모름)

**출력 예시:**
```
[버튼 짧게 누름]
"주변을 확인합니다. 천천히 한 바퀴 도세요."
[회전]
"삐— 확인 완료. 네 개 찾았습니다."
"정면 2미터, 의자."
"오른쪽 45도, 사람."
"오른쪽 90도, 자동차."
"뒤쪽, 벤치 둘."
```

### 구현 순서

1. 스위치 배선 + 롱프레스 분기 (`sensor/button_handler.py`) — **부품 도착 후, 크리티컬 패스 아님** (§0-2 참고). 그전엔 소프트웨어 트리거로 2~5번 먼저 진행
2. 스캔 시작/종료 상태 머신 (`main.py`) — 스캔 중엔 수동 경보 정지
3. **동기 캡처** — 프레임 + ToF를 같은 시점으로 정렬해 수집 (1-2 문제가 여기서 해결됨)
4. 중복 제거 (방법 B: 시간 기반)
5. 발화 문구 생성 + 개수 제한
6. (귀국 후, 선택) IMU 추가 → 방법 A로 교체

### 종료 조건

- 버튼 짧게 누름 → 스캔 시작 → 회전 후 5개 이하로 요약된 발화가 나온다
- 정지 상태에서 같은 공간을 3회 반복 스캔했을 때 가장 가까운 1~2개 물체가 매번 비슷하게 보고된다 (방법B는 러프해도 되지만 결과가 매번 완전히 다르면 안 됨)
- 최소 조건: 방법B 스캔이 실외에서 1회 이상 성공적으로 동작 — 이게 "STEP1+4만으로 멈춰도 되는" 라인의 기준이다

> ### 🛑 여기서 멈춰도 된다
> STEP 1 + 4 만 해도 **"측정으로 방향을 바꾸고, 이 하드웨어가 잘하는 기능을 만들었다"** 가 완성된다.
> 이게 이번 사이클의 목표선이다 (맨 위 배너 참고).

`config.py`의 `HIGH_RISK_DIST_CM`, `MID_RISK_DIST_CM`, `ALERT_REMINDER_SEC` 조정.

**이것만으로 분당 10회가 1~2회로 떨어질 것으로 예상된다.** KPI가 자연히 맞는다.

## 5. STEP 6 — 글로 남기기 (각 반나절) ⭐ 분야가 안 정해졌다면 특히

`CLAUDE.md`에 묻혀 있는 이야기 중 밖에 내놨을 때 값이 나가는 것 3개. 각각 A4 1~2장.
**의존성 없음 — 언제든 병행 가능.**

> **선행 (반나절, 8-1):** AWB 마젠타 버그 수정. `vision/auto_white_balance.py`의 `update()`에서
> 포화 픽셀 보호(`sat = frame.max(axis=2) >= 250` → 게인 적용 취소). 탐지 성능엔 영향 없지만
> 포트폴리오 스크린샷 품질 때문에 STEP 6 전에 고친다.

### ① TTS 발화가 비전을 실명시키던 버그
발화 중 FPS를 8로 낮추는데(`TTS_ACTIVE_VISION_FPS`) fallback 임계값도 8이라
**정확히 같아서** EMA가 경계를 오르내렸다. → 경보를 말하는 순간마다 비전이 스스로를 실명 처리.
발화 0.85~1.1초 뒤 진입이 매번 재현, 분당 9회.

**왜 좋은가:** "안전장치가 자기를 무력화한다"는 구조적 아이러니 + 하필 임계값이 같아서 발견이 늦었다는 디테일.

### ② 소리가 안 나는데 서비스는 정상이던 문제
`hp switch`는 DAPM 위젯이라 유휴 상태에서 커널이 즉시 off로 되돌린다. 진짜로 막던 건 `Headphone`.
로그의 "부팅 오디오 큐 재생"은 **재생 시도**만 뜻해서 무음 진단에 못 쓴다.

**왜 좋은가:** 리눅스 오디오 서브시스템을 실제로 파본 사람만 아는 내용.

### ③ aarch64에서 ctypes 핸들이 잘려 segfault
`restype = c_void_p`라 핸들이 Python int인데, `argtypes` 없이 넘기면 32비트로 잘린다.

**왜 좋은가:** 64비트 FFI 경계 문제. 짧지만 밀도가 높다.

### 쓰는 법 (부담 줄이기)

```
1. 증상 — 사용자 눈에 뭐가 이상했나
2. 왜 어려웠나 — 왜 바로 안 보였나
3. 원인 — 실제로 뭐였나
4. 어떻게 알았나 — 어떤 측정으로 확정했나   ← 제일 중요
```

4번이 대부분의 포트폴리오에 없는 항목이다.

> 셋 중 어느 걸 쓸 때 시간 가는 줄 몰랐는지가 힌트가 된다.
> ①은 시스템 설계, ②는 리눅스/드라이버, ③은 저수준 FFI — 서로 결이 꽤 다르다.

## 6. 이번엔 안 하는 것 (귀국 후 재검토)

- **STEP 2 — VL53L5CX 주문:** 지면+정면+머리높이를 8×8존 센서 하나로 동시에 보는 경로. 예산(~5만원)·배송·미검증 통합 리스크로 보류. `sensor/` HAL만 갈아끼우면 되는 구조라 언제 재개해도 됨.
- **STEP 3 — 지면 평면 피팅:** STEP 2 센서로 존별 기대거리(`h/sin(θ+row각도)`)를 계산해 낙하 감지. STEP 2가 보류라 자동 보류.
- **모션블러:** 노출 상한 89.7% 고착 — `CSI_AE_EXPOSURE_MAX`를 1200쯤으로 낮춰볼 여지 있음. 스캔 모드(서서 촬영)에선 문제 안 됨, 걷는 중 탐지가 계속 문제일 때만 본다.
- **ToF 세 숫자 불일치(raw/filtered/경보):** 스캔 경로는 STEP 4의 동기 캡처로 이미 해결. 걷는 경로는 STEP 3 재개 시 같이 본다.
- **하지 않아도 되는 것:** ToF ROI 상반부 자르기(방향과 정반대) / 큰 YOLO로 교체(탐지 없음의 원인은 모델 크기가 아니라 COCO에 벽·지면 클래스가 없어서) / 커스텀 데이터셋 학습(몇 주 소요, ToF가 할 일) / 코드 리팩터링(구조는 멀쩡함).
