## Phase 2 · 로그 동기화 + CSV 분석 🔲
> 목표: Pi에 쌓인 운영 CSV 로그를 PC로 수집하고, 1.0에서 이관된 6-2 분석 수행  
> **범위 제한:** PC에서 수동 rsync pull만 정식 구현. Pi 쪽 systemd timer 자동 push는 수동 방식이 실제로 불편해진 뒤에 재검토 (범위 제외)
> **⚠️ tailscale 반영 필요(2026-07-25):** "실외 로그는 귀가 후 동기화" 전제는 tailscale 도입으로 무의미해짐(밖에서도 pull 가능). 또 auto-push 제외 근거였던 "PC 꺼짐 실패 처리"도 노트북이 상시 tailscale 서버라 약해짐. → **당장은 수동 pull 유지**(가장 단순)하되, 근거는 갱신. pull 대상 alias `raseyes`는 이제 tailscale 경유라 어느 네트워크서든 동작.

| # | 작업 | 비고 | 상태 |
|---|------|------|------|
| 2-1 | 로그 pull 스크립트 작성 | `scripts/pull_logs.sh` — CSV + `logs/events/` 클립을 `logs_archive/`로 수집. 전용 데몬 없음 | ✅ |
| 2-2 | CSV 로그 분석 (1.0의 6-2 이관) | 분석 도구 `scripts/analyze_logs.py` 완성 (세션 분할 · 함정 2건 보정 · KPI 대조). **실측 분석은 Pi 전원 인가 후 수행 예정** | 🔲 |
| 2-3 | 분석 결과 문서화 및 UX 개선점 도출 | 오탐지 KPI(< 1회/분) 실측치 확인 포함. 2-2 실행 이후 진행 | 🔲 |
| 2-4 | CSV에 가림 감지 카운터 추가 *(2026-07-27 추가)* | `FIELDNAMES`에 `occlusion_alerts` 추가. 누적 총계가 아니라 **로그 주기(1초) 내 증가분** — 시간 정렬이 쉬움 | ✅ |

**2-1 구현 시 발견한 추가 함정 (로드맵 초안에 없던 것)**
`CsvLogger.open()`이 `mode="w"`라 **Pi는 프로세스 재시작마다 CSV를 덮어쓴다**(로드맵이 적었던 "단일 append 파일"이 아님). 같은 파일명으로 pull하면 이전 세션 로그가 아카이브에서 사라지므로, `pull_logs.sh`는 원격 파일의 mtime을 파일명에 박아(`raseyes_log_<YYYYMMDD_HHMMSS>.csv`) 세션별로 보존한다. 같은 세션을 다시 pull해도 파일명이 같아 멱등하다.

**분석 시 알려진 데이터 함정 (2026-07-27 실측 확인)**

| 함정 | 내용 |
|------|------|
| 타임존 경계 | Pi 타임존이 `Asia/Shanghai`(+0800)로 잡혀 있었고 CSV는 오프셋 표기 없는 로컬시각 기록. **2026-07-27에 `Asia/Seoul`로 변경 예정** → 변경 이전 행(약 1,261행)은 실제 한국 시각보다 **1시간 이름**. 분석 시 +1h 보정 필요 |
| 세션 첫 행 이상치 | 세션 첫 행의 `fps`가 EMA 초기화 아티팩트로 비정상값을 가짐(실측 예: `1164`). FPS 통계 산출 시 세션 첫 행 제외 |

**Phase 2 완료 기준:** 착용 테스트 후 명령 한 번으로 로그가 PC에 수집되고, CSV 분석 결과가 문서로 정리됨. *(수집·분석 도구는 완성. Pi 전원 인가 후 `bash scripts/pull_logs.sh` → `python scripts/analyze_logs.py logs_archive/*.csv` 실행하면 2-2/2-3 마감.)*

## Phase 3 · 경고 이벤트 클립 저장 ✅ *(2026-07-27 구현 완료, 실기기 검증 잔여)*
> 목표: 오탐지 분석·유지보수를 위해 경고 발생 시점 전후 프레임을 저장 (상시 녹화 금지 — 저장소 수명·성능 KPI·프라이버시 고려)

### 설계 확정 사항 (2026-07-18 초안 → 2026-07-27 전면 확정)

| 항목 | 결정 |
|------|------|
| 저장 트리거 | **HIGH 경보 단독** *(2026-07-27 변경)*. 당초 "가림 감지 등 시스템 이상"도 포함했으나 제외 — 가림 클립은 정적 화면이라 정보량이 낮음. MID는 저장량 문제로 제외. 트리거가 1종이라 쿨다운 상태는 `float` 하나로 충분 |
| 저장 형식 | **저빈도 JPEG 시퀀스** — mp4 인코딩 없음. Pi 실측 **3.15ms/프레임**(q=85, 640×480 노이즈=최악 케이스)이라 메인 루프에서 즉시 인코딩해도 15FPS 프레임 예산(66ms) 대비 무시 가능 → **별도 인코딩 스레드 불필요** |
| 링 버퍼 샘플링 | **시간 기준 200ms 간격** *(2026-07-27 확정)*. 프레임 카운트 기준은 금지 — 저전력 모드(4FPS)에서 1.3장/초로 폭락함. HIGH 직전 구간은 거리 > 200cm였을 가능성이 커서 **대부분 저전력 상태**라는 것이 근거 |
| 클립 범위 | 이벤트 전 5초 + 후 3초. 버퍼는 **전 5초분만** 유지하고, 트리거 시 즉시 복사 → 이후 3초는 별도 리스트로 수집 |
| 오버랩 처리 | **(b) 쿨다운 30초**(트리거 시각 기준). 창 연장 merge(a)는 클립 길이가 가변이 되어 용량 예측·보존 한도 계산이 무너지므로 제외. **불변식: `CLIP_COOLDOWN_SEC > CLIP_POST_SEC`** — 깨지면 "후속 수집 중 재트리거"가 발생해 위 버퍼 설계가 중첩 지뢰밭이 됨 |
| 메타데이터 | 프레임별 타임스탬프·탐지 결과(레이블, bbox, confidence) + **프레임별 ToF 거리** + **쿨다운 중 억제된 HIGH 횟수**. ToF 값이 없으면 ToF 오작동發 오탐을 판별할 수 없음(HIGH는 비전 단독이 아니라 융합 판정). CSV에도 tof가 있으나 1Hz라 5FPS 클립과 시간 정렬 불가 |
| 저장 위치·명명 | `logs/events/<YYYYMMDD_HHMMSS>_<label>_<dist>cm/` (예: `20260727_105646_chair_34cm/`), 내부에 `meta.json` + `000.jpg`… . 폴더명만으로 훑을 수 있게 라벨·거리 포함. ⚠️ **배포 rsync 제외 목록에 `logs/events/` 필수** — `logs/*.csv`만으로는 하위 디렉터리가 안 걸러져 `--delete`에 클립이 전멸함 |
| 보존 한도 | **개수 30개 AND 보존 7일** — 둘 중 하나만 넘어도 삭제. 근거는 디스크 절약이 **아님**(Pi 여유 52GB, 30개 60~90MB = 0.17%). 실제 근거는 ①사람이 검토 가능한 양 ②행인 얼굴 자동 소멸 |
| rotation 시점 | **프로세스 시작 시 1회 + 클립 덤프 시**. 기간 한도는 아무 일이 없어도 넘으므로 덤프 시점 검사만으로는 부족 |
| Mock 모드 | **동작시킴**. mock 비전이 정상 ndarray(`np.zeros`)를 주므로 폴더 생성·전후 범위·rotation·쿨다운을 실기기 없이 PC에서 검증 가능 |
| 상수 관리 | 버퍼 FPS · 전/후 초 · 쿨다운 · JPEG 품질 · 보존 한도(개수/일) · 저장 경로 모두 `config.py` 상수화 |
| 프라이버시 | **문서 명시로 갈음** *(2026-07-27 결정)*. 최대 7일 · 30클립(약 1,200프레임)의 행인 얼굴이 로컬 잔존. 현재는 **1인 개인 프로토타입 · 로컬 전용 한정**이며, 3자 배포·공개 시 재검토 필요. 얼굴 블러는 프레임당 추가 추론이 KPI를 위협해 PoC 단계에선 과잉으로 판단 |

**config.py 신규 상수 (8개)**

```python
CLIP_BUFFER_FPS: int = 5              # 링 버퍼 적재 주기 (200ms 간격)
CLIP_PRE_SEC: float = 5.0             # 이벤트 전 보관 구간
CLIP_POST_SEC: float = 3.0            # 이벤트 후 수집 구간
CLIP_COOLDOWN_SEC: float = 30.0       # 오버랩 억제. 반드시 CLIP_POST_SEC보다 커야 함
CLIP_JPEG_QUALITY: int = 85           # Pi 실측 3.15ms/프레임
CLIP_RETENTION_MAX_DIRS: int = 30
CLIP_RETENTION_MAX_AGE_DAYS: int = 7
CLIP_DIR: str = "logs/events"
```

**구현 중 확정한 세부 사항 (설계표에 없던 것)**

| 항목 | 결정 |
|------|------|
| 억제 카운터 귀속 | 덤프는 트리거+3초, 쿨다운은 30초라 **자기 클립의 쿨다운 억제 수를 자기 meta에 담는 것이 원리상 불가능**. 대신 직전 쿨다운 구간의 억제 수를 다음 클립의 `suppressed_high_since_prev_clip`에 기록 — 정보 손실 없음 |
| ToF 거리 기록 | 원시(`raw_distance_cm`)와 필터 후(`filtered_distance_cm`) **둘 다** 프레임별로 기록. HIGH는 융합 판정이라 필터 입력값이 있어야 ToF 오작동發 오탐을 가려낼 수 있음 |
| 중복 프레임 스킵 | 저전력 4FPS(250ms)는 샘플링 주기(200ms)보다 느려 같은 프레임이 두 번 전달됨 → `frame_ts` 동일 시 건너뜀 |
| 코드 배치 | `main.py`는 오케스트레이션만 담당한다는 규칙에 따라 `logs/clip_recorder.py`로 분리. 메인 루프 개입은 `offer_frame()`/`trigger()` 2줄 |
| 인코딩 위치 | E2E 레이턴시 측정 블록 **뒤**에 배치 — JPEG 인코딩 시간이 레이턴시 EMA에 섞여 `LATENCY_WARN_THRESHOLD_MS` 경고를 오염시키지 않게 함 |
| 미완 클립 처리 | SIGTERM은 `_stop_event`만 세트해 후속 3초 수집이 끊김 → 부분 클립을 저장하지 않고 **폐기**(`close()`). 부분 저장은 복잡도 대비 이득이 없음 |
| 실패 격리 | 인코딩·기록·rotation 실패는 전부 `logger.error`로 삼킨다. 클립 저장 실패가 본 기능(장애물 경고)을 죽이면 안 됨 |

## 1. Pi 배포 ⚠️ 가장 위험한 단계

```bash
# 반드시 dry-run 먼저. logs/events/ 가 삭제(deleting) 목록에 없는지 눈으로 확인할 것
rsync -avn --delete \
  --exclude='.git/' --exclude='.venv/' --exclude='models/' \
  --exclude='logs/*.csv' --exclude='logs/events/' --exclude='*.md' \
  ./ raseyes:~/RasEyes/
```

- `logs/*.csv` 패턴은 **하위 디렉터리를 걸러내지 못한다.** `logs/events/` 제외를 빠뜨리면 Pi에 쌓인 클립이 배포 한 번에 전멸하고 Phase 3 자체가 무의미해진다.
- dry-run 출력에 `deleting logs/events/...`가 보이면 **즉시 중단**하고 제외 옵션을 고칠 것.
- 확인 후 `-n`을 빼고 실제 실행.
- 재시작은 사용자가 직접: `ssh -t raseyes "sudo systemctl restart raseyes.service"`

## 4. 클립 운영 파라미터 재조정 (실측 후)

`config.py`의 `CLIP_*` 상수는 전부 책상 위 추정치다. 실사용 데이터로 다시 볼 것:

| 상수 | 재검토 기준 |
|------|-------------|
| `CLIP_COOLDOWN_SEC` (30초) | 억제 카운터(`suppressed_high_since_prev_clip`)가 지속적으로 크면 놓치는 이벤트가 많다는 뜻 |
| `CLIP_PRE_SEC` (5초) | 클립을 실제로 봤을 때 "원인 장면"이 앞에 잘려 있으면 늘릴 것 |
| `CLIP_RETENTION_MAX_DIRS` (30) | 하루 생성량 실측 후 조정. 근거는 디스크가 아니라 "사람이 검토 가능한 양" |

> ⚠️ **불변식: `CLIP_COOLDOWN_SEC > CLIP_POST_SEC`.** 깨면 후속 수집 중 재트리거가 발생해 버퍼 설계가 무너진다.
