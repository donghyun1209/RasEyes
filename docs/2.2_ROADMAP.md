## 🚀 단계별 작업 계획

### 🔍 Phase 0 — 통신 수단 확정 ✅ **완료**

**Pi에 온보드 블루투스가 없다** (2026-08-28 실측). `hciconfig`·`bluetoothctl` 무출력,
`/sys/class/bluetooth/` 비어 있음, `lsusb`엔 WiFi 동글(MT7601U)뿐. 커널 모듈은 로드돼
있으나 refcount 0이라 "모듈만 미로드"가 아니라 물리 어댑터 부재다 — Orange Pi 5
기본형이 맞았다 (온보드 BT는 5B/5 Plus 계열).

원안은 여기서 **핫스팟 TCP로 선회**하는 것이었으나 **USB BLE 동글**을 택했다.
TCP는 부품비가 0원이지만 폰이 AP 노릇을 하는 대가가 크다 — 배터리 소모, 그리고
**매 외출마다 설정에서 핫스팟을 켜야 한다**(iOS는 연결 기기가 없으면 90초 뒤 자동
종료). 매일 쓸 기기의 사용 마찰로는 부적절하다고 봤다.

**동글 실측 완료** (2026-08-30 · Barrot 칩 BT5.3 `33fa:0001` · 5천원대):

| 확인 | 결과 |
|---|---|
| `hci0` | ✅ UP RUNNING — 펌웨어 파일 없이 표준 `btusb`가 인식 |
| `Roles` | ✅ central + **peripheral** |
| **LE 광고 등록** | ✅ `Advertising object registered` · `ActiveInstances: 1` |
| LE 스캔 | ✅ 주변 기기 정상 탐지 |
| 소프트웨어 | ✅ BlueZ 5.64 · `dbus-python` 1.2.18 — **추가 의존성 0** |

광고를 실제로 띄워 확인했으므로 **"Pi를 BLE 주변장치로 띄울 수 있는가"라는 Phase 2의
최대 미지수가 해소됐다.** 남은 GATT 서비스 등록은 같은 D-Bus API 계열이다.

### 📱 Phase 1 — iOS 앱 뼈대 구성
> **Pi 불필요** · 소스·Xcode 프로젝트 완료 · 코드표 검증 완료(2026-08-30) · 맥에서 잔여 2건

#### 지도 SDK 결정 변경 (2026-08-28)

**Google Maps SDK → MapKit + TMAP 보행자 경로안내 API.**

원안(Google Maps)은 착수 전에 Google Cloud 프로젝트 생성·**신용카드 등록**·API 3종
활성화가 선행돼야 했고, 무엇보다 **국내 도보 경로가 자주 비어(`ZERO_RESULTS`) 출국 전
국내 테스트(Phase 4)에 쓸 수 없었다.** 국내 검증을 앞당기는 것이 목표이므로 갈아탔다.

국내에서 실제로 막히는 것은 **경로 계산(`MKDirections`) 하나뿐**이다 — 지도·현재 위치·
장소 검색은 MapKit으로 한국에서 정상 동작한다. 그래서 경로만 `RouteProvider` 프로토콜로
분리해 지역별 구현을 갈아끼운다. **Pi 쪽 HAL과 같은 패턴**이라 화면·통신 계층은 수정이 없다.

| 기능 | 수단 | 한국 | 파리 |
|---|---|:---:|:---:|
| 지도 · 현재 위치 | MapKit + CoreLocation | ✅ | ✅ |
| 목적지 검색 | `MKLocalSearch` | ✅ | ✅ |
| 도보 턴바이턴 | **TMAP 보행자 경로안내** (구현 완료) | ✅ | ❌ |
| 도보 턴바이턴 | OpenRouteService (미구현) | ⚪ | ✅ |

TMAP은 SDK 설치 없이 REST 호출 하나면 되고, 무료 쿼터에 **결제 수단 등록을 요구하지
않는다.** 횡단보도·육교·지하보도를 별도 코드로 구분해줘 시각장애인 안내에 유리하다.
파리용 `ORSRouteProvider`는 출국 전에 추가한다.

#### 작성 완료 (`ios/RasEyesApp/RasEyesApp/`, 5개 파일 + 키 템플릿)

| 파일 | 역할 |
|---|---|
| `RouteProvider.swift` | 제공자 프로토콜 + `ManeuverCode`·`RouteStep` 정규화 모델 |
| `TmapRouteProvider.swift` | TMAP GeoJSON 호출·파싱 (한국) |
| `LocationManager.swift` | CoreLocation 권한·좌표 |
| `ContentView.swift` | 지도 · 검색 · 경로 지시 목록 |
| `RasEyesNavApp.swift` | 앱 진입점 |
| `Secrets.example.swift` | TMAP 키 템플릿 — **한 단계 위**(`ios/RasEyesApp/`)에 둔다 |

Xcode 프로젝트도 생성되어 커밋돼 있다(`ios/RasEyesApp/RasEyesApp.xcodeproj`).
**Xcode 16의 폴더 동기화 방식**이라 `RasEyesApp/RasEyesApp/` 안의 `.swift`는 드래그 없이
자동으로 빌드에 포함된다. 그래서 키 템플릿을 그 폴더에 두면 `Secrets.swift`와
`enum Secrets`가 중복 선언되어 빌드가 깨진다 — 2026-08-28에 이 상태였던 것을 고쳤다
(같은 날 소스가 두 벌로 중복돼 있던 것도 정리했다).

* 음성 검색(`Speech` STT)은 후순위로 미뤘다 — 시간 부족 시 생략 대상 1순위(리스크 레지스터).
* 경로 지시 각 행에 **Pi로 보낼 압축 코드(`R|50`)를 화면에 함께 표시**한다.
  Phase 2 통신을 붙이기 전에 무엇이 나갈지 눈으로 검증하기 위한 것이다.
* Pi의 Piper TTS가 **영어 모델**이므로 TMAP의 한국어 원문은 전송하지 않는다.
  앱이 코드로 정규화하고 Pi가 영어 문장을 조립한다(Phase 3 설계 그대로).

**✅ 완료 기준:** 폰에서 목적지를 입력하면 경로 텍스트(예: 50m 직진 후 우회전)가 화면에 제대로 뜨는지 확인.

**잔여 작업 (맥에서, 약 10분):** 맥의 클로드에 붙여넣을 프롬프트가 **`ios/MAC_PROMPT.md`** 에 있다.
1. TMAP 앱 키 발급 → `RasEyesApp/RasEyesApp/Secrets.swift`
2. 시뮬레이터 위치를 서울로 지정하고 빌드·실행 확인

**PC에서 처리 완료 (2026-08-30):**
* **위치 권한 문구** — 맥 GUI 작업인 줄 알았으나 아니었다. 이 프로젝트는
  `GENERATE_INFOPLIST_FILE = YES`라 Info.plist 파일이 없고 `INFOPLIST_KEY_*` 빌드 설정으로
  관리된다. `project.pbxproj`에 직접 넣어 해소했다.
* **빌드 blocker 제거** — `SWIFT_OBJC_BRIDGING_HEADER`가 저장소에 **없는 헤더 파일**을
  가리키고 있어 맥에서 빌드하는 즉시 실패할 상태였다. Swift 전용 프로젝트라 설정을 지웠다.

배포 타겟(`IPHONEOS_DEPLOYMENT_TARGET = 26.5`)은 **그대로 둔다** — 실기로 쓸 아이폰이
그보다 높아 문제가 없다 (2026-08-28 확인).

#### `turnType` 코드표 검증 완료 (2026-08-30)

공식 문서([경로안내 샘플예제](https://tmap-skopenapi.readme.io/reference/%EA%B2%BD%EB%A1%9C%EC%95%88%EB%82%B4-%EC%83%98%ED%94%8C%EC%98%88%EC%A0%9C))로
30개 코드를 대조해 **오류 세 건**을 잡았다. 전체 표는 `ios/README.md` 부록에 있다.

| 코드 | 기존 | 공식 | |
|---:|---|---|---|
| `128` | 에스컬레이터 | **경사로 진입** | 오매핑 — 시각장애인에게 그냥 틀린 안내다 |
| `130` | 엘리베이터 | **표에 없음** | 존재하지 않는 코드였다 |
| `218` | (누락) | 엘리베이터 | 진짜 엘리베이터가 `.unknown`으로 떨어지고 있었다 |

누락됐던 `129`(계단+경사로)·`233`(직진 임시)·`184~189`(경유지)도 채웠다.
**횡단보도는 방향까지 나눴다**(`212` 좌측 → `XL`, `213` 우측 → `XR`, 시계방향 4종).
시각장애인에게 좌/우 횡단보도 구분은 안전에 직결되고, 최장 코드가 `X10|1500` = 8바이트라
BLE MTU(20바이트)에 여유가 있다.

> 표에 없는 코드는 계속 `.unknown`으로 떨어뜨리고 원문을 화면에 남긴다 — 실행 시 **주황 배지**.
> 모르는 코드를 "직진"으로 몰아넣으면 **회전을 놓치고도 조용히 지나가기 때문이다.**
> 공식표의 `1~7`("안내 없음")은 `Point`로 오는지 미확인이라 일부러 매핑하지 않았다.

### 📡 Phase 2 — 통신 계층 (BLE GATT)
> **Pi 필요** · 동글·광고까지 실측 확인됨(Phase 0) — **착수 가능**

1. **최소 기능(Spike) 검증:** Pi를 주변장치로 띄우고 iOS가 붙어서 **단순 문자열 송수신**이 되는지 최우선 확인.
2. **MTU 대응:** iOS 기본 전송 한계(20바이트)를 넘지 않도록 짧은 코드 형식(`R|50`)으로 보내고 Pi에서 문장을 조립.
3. **HAL 적용 & 예외 처리:** 기존 패턴대로 `ble_nav_hal.py` 생성. 연결 끊김 시 메인 루프에 영향 없도록 **Fail-soft** 처리.
4. **iOS 백그라운드:** 화면이 꺼져도 추적 및 전송이 되도록 백그라운드 권한 부여.

**✅ 완료 기준:** 주머니에 폰(화면 끄기)을 넣은 상태에서 Pi가 경로 문자열을 끊기지 않고 수신.

### 🔊 Phase 3 — 안내 발화 통합
> **Pi 내부**

1. **TTS 연결:** 수신된 경로 코드를 문장(`"Turn right in 50 meters"`)으로 만들어 기존 TTS 큐에 삽입.
2. **우선순위 관리:**
   * 장애물 경보(Danger)가 **항상** 턴바이턴 안내를 덮어씌움 (길 안내는 그 뒤에 재생).
   * '둘러보기 모드' 동작 중에는 턴바이턴 발화를 보류함.
3. **발화 밀림 방지:** 오래된 GPS 지시는 TTS 큐에서 비우고 최신 지시로 덮어쓰기 (태그 도입 제안).

---

### 🚶 Phase 4 — 실기 및 현지 검증

1. 출국 전(**9/2 이전**) 국내에서 최소 1회 야외 통합 테스트 실시 (지연시간, 폰 배터리 등).
2. 파리 도착 후 실사용하며 튜닝 진행.
